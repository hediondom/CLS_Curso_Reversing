El Subsistema Gráfico en Modo Kernel (win32k) y la Tabla de Servicios Sombra

Propósito y Relevancia

En la arquitectura de Windows, el modo kernel no solo alberga los servicios de sistema estándar del ejecutivo y del gestor de memoria (ntoskrnl.exe). También aloja el subsistema de ventanas, interfaz gráfica y gestión de dispositivos de entrada (GDI y USER). Este subsistema está implementado en controladores de sistema especiales (win32kbase.sys, win32kfull.sys y el driver legado win32k.sys). Con más de 1.200 llamadas al sistema que históricamente han constituido la mayor superficie de ataques de escalada local de privilegios (LPE) en Windows, su análisis es obligatorio para cualquier investigador de seguridad.

1. Descomposición de Win32k y Arquitectura Modular

En versiones antiguas de Windows (hasta Windows 7 y 8.1), toda la lógica gráfica residía en un único driver monolítico de gran tamaño: win32k.sys. Desde Windows 10, Microsoft refactorizó el subsistema en módulos especializados para reducir el acoplamiento y mejorar la telemetría:

|                         ESPACIO DE USUARIO (x64)                            |
|  [ user32.dll ]               [ gdi32.dll / gdi32full.dll ]                 |
|         │                                    │                              |

                                       │ (syscall)
+──────────────────────────────────────┼──────────────────────────────────────+
|                         ESPACIO DE KERNEL (x64)                             |
|                                      ▼                                      |
|  KeServiceDescriptorTableShadow [Índice 1: Descriptor de Servicios Win32k]  |
|                                      │                                      |
|         ┌────────────────────────────┴─────────────────────────────┐        |
|         ▼                                                          ▼        |
|  win32kbase.sys                                             win32kfull.sys  |
|  (Gestión de memoria gráfica,                               (Lógica pesada: |
|   handles de ventana, threads GUI,                          mensajes WM_*,  |
|   DirectComposition y primitivas base)                      renderizado GDI)|
+─────────────────────────────────────────────────────────────────────────────+

El Módulo de Transición en Modo Usuario: win32u.dll

Históricamente, las funciones de user32.dll (como CreateWindowExW) invocaban directamente la instrucción syscall. En Windows 10 y 11 modernos, Microsoft centralizó todos los stubs de llamadas al sistema gráficas dentro de una DLL de bajo nivel llamada win32u.dll. Cualquier llamada de alto nivel en user32.dll o gdi32.dll pasa primero por un stub NtUser* o NtGdi* dentro de win32u.dll.

2. Despacho por la Tabla Sombra: KeServiceDescriptorTableShadow

En la Lección 2.15 vimos cómo las llamadas al sistema nativas (NtOpenProcess, NtAllocateVirtualMemory) se despachan mediante la tabla global exportada KeServiceDescriptorTable. Sin embargo, los servicios gráficos utilizan una tabla extendida no exportada: KeServiceDescriptorTableShadow.

Estructura de KSERVICE_TABLE_DESCRIPTOR y Navegación en WinDbg

La tabla sombra contiene un arreglo de dos descriptores de servicio (KSERVICE_TABLE_DESCRIPTOR), cada uno de 32 bytes (en x64):

Offset (x64) Campo Tipo Significado y Función
+0x00BasePULONG_PTRPuntero a la tabla de direcciones relativas de las rutinas de servicio (Service Table Base).
+0x08CountPULONGPuntero al arreglo de contadores de invocaciones de cada syscall (Service Counter Table Base).
+0x10LimitULONGCantidad total de llamadas al sistema registradas en la tabla (ej. ~0x1C0 para ntoskrnl, ~0x500 para win32k).
+0x18NumberPUCHARPuntero al arreglo que contiene el número de bytes de argumentos pasados en el stack por cada llamada.
  • Entrada 0 (KeServiceDescriptorTableShadow[0], offset +0x00): Descriptor idéntico a KeServiceDescriptorTable para los servicios nativos del ejecutivo de ntoskrnl.exe.
  • Entrada 1 (KeServiceDescriptorTableShadow[1], offset +0x20): Descriptor reservado para el subsistema gráfico despachado por win32kbase.sys y win32kfull.sys.
$$ Inspeccionar los descriptores de KeServiceDescriptorTableShadow en WinDbg
kd> dq nt!KeServiceDescriptorTableShadow L8
$$ El primer QWORD en +0x20 es el puntero Base de win32k:
kd> dps poi(nt!KeServiceDescriptorTableShadow + 0x20) L20

Conversión de Números de Servicio (SSN Gráfico)

Las syscalls de Win32k poseen el bit 12 activo (índice de tabla 1, base 0x1000). Como los números de servicio (SSN) tanto de ntoskrnl como de win32k cambian entre builds de Windows, nunca deben asumirse como constantes fijas entre versiones. Cuando una instrucción syscall se ejecuta con EAX = 0x1000 + N:

  1. El despachador nt!KiSystemCall64 extrae el índice de tabla ((EAX >> 12) & 1) y comprueba si el número de servicio pertenece al rango gráfico (0x1000+).
  2. Obtiene el puntero al _KTHREAD actual desde GS:[0x188] (KPCR.Prcb.CurrentThread) y verifica si el hilo ya fue promovido a GUI Thread comprobando que el campo _KTHREAD->Win32Thread no sea nulo (ubicado en el offset +0x1C8 de nt!_KTHREAD en Windows 10 22H2 Build 19045, Windows 11 23H2 Build 22631 y Windows 11 24H2 Build 26100).
  3. Si el hilo aún es estándar (no GUI), el kernel invoca nt!PsConvertToGuiThread: valida que el proceso no tenga activa la política Win32k Lockdown, asigna el stack de kernel extendido requerido por el subsistema gráfico, inicializa Win32Thread y cambia el índice de tabla de servicios del hilo hacia KeServiceDescriptorTableShadow.
  4. El kernel toma el descriptor de índice 1 de KeServiceDescriptorTableShadow (offset +0x20) y calcula la dirección destino sumando a Base el desplazamiento relativo con signo almacenado en Base[N] >> 4.

3. El Fenómeno Crítico: Inversión de Control con KeUserModeCallback

La razón principal por la cual Win32k ha sido la mayor fuente histórica de vulnerabilidades de kernel (Use-After-Free y elevación de privilegios) es su necesidad de interactuar con el espacio de usuario mientras procesa llamadas de kernel:

Mecánica de Inversión

Cuando una función en modo kernel dentro de win32kfull.sys necesita notificar a una ventana (por ejemplo, para ejecutar un hook de ventana global o despachar un mensaje WM_NCCREATE), el kernel no puede ejecutar la función de ventana directamente en modo kernel.

  1. El driver de kernel invoca nt!KeUserModeCallback.
  2. Esta función guarda el estado actual del stack de kernel, prepara un frame de retorno hacia el modo usuario y salta a la rutina ntdll!KiUserCallbackDispatcher en el proceso.
  3. El código de usuario procesa el mensaje (ejecutando callbacks como user32!__ClientLoadLibrary).
  4. Al concluir, el modo usuario invoca la syscall nativa NtCallbackReturn para devolver el control al driver de kernel en el punto exacto donde se suspendió.

El Riesgo de Seguridad (Race Conditions y Reentrancia)

Durante el tiempo en que el control está en espacio de usuario a través de KeUserModeCallback, el proceso puede ejecutar código malicioso que destruya o libere la ventana o el objeto GDI (DestroyWindow) sobre el cual el kernel estaba operando. Cuando el control regresa a win32kfull.sys, si el driver asume que el objeto sigue existiendo en el puntero original sin revalidar su estado de bloqueo, se produce un fallo clásico de Use-After-Free (UAF) en espacio de kernel.

4. Mitigación de Superficie de Ataque: Win32k System Call Lockdown

Dado que el subsistema gráfico en modo kernel (win32k.sys, win32kfull.sys y win32kbase.sys) expone más de 1.100 syscalls en la KeServiceDescriptorTableShadow y ha concentrado históricamente el mayor volumen de vulnerabilidades de elevación de privilegios (EoP) utilizadas para escapar de sandboxes de navegadores, Windows 10/11 incorpora la política de mitigación de proceso Win32k System Call Disable Policy (conocida como Win32k Lockdown).

Procesos altamente expuestos a contenido no confiable (como los procesos de renderizado de Google Chrome, Microsoft Edge y sandboxes de visualización) activan esta mitigación para auto-despojarse permanentemente del derecho de invocar llamadas a la tabla sombra. Si un exploit intenta invocar cualquier syscall gráfica (0x1000+), el despachador de kernel intercepta la transición y devuelve acceso denegado.

4.1. Mecanismo Interno en KiConvertToGuiThread y _EPROCESS

Cuando un proceso habilita esta política mediante SetProcessMitigationPolicy(ProcessSystemCallDisablePolicy, ...) o al ser creado por un broker mediante el atributo PROC_THREAD_ATTRIBUTE_MITIGATION_POLICY con la bandera PROCESS_CREATION_MITIGATION_POLICY_WIN32K_SYSTEM_CALL_DISABLE_ALWAYS_ON, el kernel activa el bit DisableWin32kSystemCalls (bit 0x04) dentro del campo MitigationFlags de la estructura nt!_EPROCESS.

El bloqueo no ocurre parcheando la tabla SSDT Shadow, sino cortando de raíz la transición del hilo en PsConvertToGuiThread / KiConvertToGuiThread:

  1. Un hilo no-GUI (cuyo KTHREAD->ServiceTable apunta a KeServiceDescriptorTable) intenta invocar cualquier syscall del rango 0x1000..0x1FFF (por ejemplo, NtUserCreateWindowEx o NtGdiBitBlt).
  2. El despachador de syscalls KiSystemServiceRepeat detecta que el índice pertenece a la tabla #1 (Win32k), la cual está vacía en la tabla estándar, y llama a KiConvertToGuiThread → PsConvertToGuiThread.
  3. Al inicio de PsConvertToGuiThread, el kernel inspecciona Process->MitigationFlagsValues.DisableWin32kSystemCalls. Si el bit vale 1, aborta inmediatamente la asignación del _W32THREAD, impide que KTHREAD->ServiceTable apunte a KeServiceDescriptorTableShadow y devuelve STATUS_ACCESS_DENIED (0xC0000022) (o genera un fallo de auditoría ETW si se configuró en modo Audit).
// Activación programática de Win32k Lockdown desde el propio proceso en Ring 3
#include <windows.h>

BOOL EnableWin32kLockdown(void) {
    PROCESS_MITIGATION_SYSTEM_CALL_DISABLE_POLICY policy = { 0 };
    policy.DisallowWin32kSystemCalls = 1;

    return SetProcessMitigationPolicy(
        ProcessSystemCallDisablePolicy,
        &policy,
        sizeof(policy)
    );
}
