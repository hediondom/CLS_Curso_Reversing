ETW y telemetría defensiva

Propósito

Comprender cómo se genera, habilita y consume telemetría ETW, dominar la sesión del sistema NT Kernel Logger, analizar la anatomía binaria del formato ETL, y auditar de forma reproducible las técnicas de evasión y manipulación de ETW (ETW Patching y Blinding) tanto en modo usuario como en modo kernel.

Prerrequisitos

  • Obligatorios: procesos/hilos (1.3); WinDbg y TTD.
  • Recomendados: 2D.10 IPC; conceptos de excepciones en 2D.11; registro de Windows (2D.3).

1. El Modelo de Arquitectura ETW

ETW separa tres roles clave: provider (emite eventos), controller (inicia sesión, habilita providers y define buffers/archivo) y consumer (procesa eventos en vivo o desde un archivo ETL).

ETW permite habilitar o deshabilitar providers en caliente, sin reiniciar el programa. Un provider registrado que nadie habilitó no emite eventos: por eso “el programa no generó nada” y “nadie estaba escuchando” se ven idénticos desde afuera.

2. La Sesión de Kernel: NT Kernel Logger

A diferencia de los proveedores de modo usuario, el kernel de Windows expone una sesión de rastreo reservada de alto rendimiento denominada NT Kernel Logger.

Identificador Global y Banderas de Activación

  • GUID de Sesión: SystemTraceControlGuid = {9e814aad-3204-11d2-9a82-006008a86939}.
  • La sesión no se suscribe a proveedores por GUID individual, sino a través del campo EnableFlags de la estructura EVENT_TRACE_PROPERTIES:
Bandera de Kernel (EnableFlags) Valor Hex (Constante) Telemetría Capturada
EVENT_TRACE_FLAG_PROCESS0x00000001 (bit 0 = 1)Creación y terminación de procesos (PID, PPID, SID, ImageFileName).
EVENT_TRACE_FLAG_THREAD0x00000002 (bit 1 = 2)Creación, destrucción y conmutación de contexto de hilos (Context Switch).
EVENT_TRACE_FLAG_IMAGE_LOAD0x00000004 (bit 2 = 4)Carga de módulos ejecutables (.exe, .dll, .sys) con dirección base y tamaño.
EVENT_TRACE_FLAG_DISK_IO0x00000100 (bit 8 = 256)Operaciones de lectura y escritura física en disco.
EVENT_TRACE_FLAG_NETWORK_TCPIP0x00010000 (bit 16)Conexiones de red TCP/UDP (send, receive, connect, disconnect).
EVENT_TRACE_FLAG_REGISTRY0x00020000 (bit 17)Creación, modificación y borrado de claves y valores del Registro.

(Nota técnica sobre EnableFlags: Valores hexadecimales canónicos definidos en evntrace.h del Windows SDK. Nótese que EVENT_TRACE_FLAG_DISK_IO corresponde estrictamente al bit 8 = 0x00000100 / 256 decimal; no debe confundirse con cero ni con valores truncados).

Control Práctico de la Sesión con logman

:: Iniciar la captura de kernel a un archivo ETL
logman start "NT Kernel Logger" -p "Windows Kernel Trace" (process,thread,img,net) -ets -o kernel_trace.etl

:: Consultar estado y estadísticas de buffers y eventos perdidos
logman query "NT Kernel Logger" -ets

:: Detener la sesión
logman stop "NT Kernel Logger" -ets

3. Anatomía y Formato Binario del Archivo ETL (.etl)

Un archivo ETL generado por ETW es una secuencia binaria estructurada de bloques de 64 KB organizados de la siguiente manera:

A. Cabecera de Buffer (WMI_BUFFER_HEADER)

Cada bloque físico de 64 KB dentro del archivo .etl comienza con una cabecera de 32 a 48 bytes:

  • BufferSize: Tamaño del bloque (típicamente 0x10000 = 64 KB).
  • SavedOffset: Desplazamiento hasta el último byte de evento escrito en el buffer.
  • CurrentOffset: Posición del cursor de escritura.
  • ReferenceTime: Timestamp de inicio del bloque en unidades de temporizador de alta resolución (RDTSC o KeQueryPerformanceCounter).

B. El Primer Registro: TRACE_LOGFILE_HEADER

El primer evento del archivo describe los metadatos globales de la captura:

  • BufferSize y VersionDetail: Versión del sistema operativo que generó la traza.
  • StartTime y EndTime: Tiempos de inicio y cierre en formato FILETIME de 64 bits.
  • TimerResolution: Resolución del temporizador del kernel (en unidades de 100 ns).
  • NumberOfProcessors y CpuSpeedInMHz: Hardware subyacente.
  • PointerSize: 4 para arquitecturas x86, 8 para x64.
  • LogFileMode: Configuración de almacenamiento (EVENT_TRACE_FILE_MODE_SEQUENTIAL, CIRCULAR, etc.).

C. Registros de Eventos (EVENT_RECORD / EVENT_HEADER)

Cada evento individual dentro de los buffers contiene una cabecera estandarizada de 80 bytes:

  1. Size (USHORT): Longitud total del registro del evento en bytes.
  2. HeaderType y Flags: Indican si el evento es de 32 o 64 bits y qué temporizador se usó.
  3. ProviderId (GUID): Identificador de 16 bytes del proveedor emisor.
  4. EventDescriptor (16 bytes):
  • Id (Identificador del evento dentro del proveedor).
  • Version (Revisión del esquema).
  • Channel (Canal de destino: Admin, Operational, Analytic, Debug).
  • Level (Severidad: Crítico, Error, Warning, Info).
  • Opcode (Operación: Start, Stop, Info).
  • Task y Keyword (Máscara de 64 bits para filtrado).
  1. ProcessId y ThreadId: PID y TID del hilo que emitió el evento.
  2. TimeStamp: Marca temporal de 64 bits.
  3. UserData / UserDataLength: Payload binario con los argumentos específicos del evento.

4. Técnicas de Manipulación y Cegado de ETW (ETW Tampering / Blinding)

En ciberseguridad defensiva e ingeniería inversa de malware, el análisis de telemetría debe contemplar cómo los atacantes neutralizan la generación de eventos:

A. Parcheo en Modo Usuario (ntdll!EtwEventWrite)

Cuando un proceso en modo usuario desea impedir que componentes de seguridad reciban eventos (como telemetría de inyección de código o AMSI), recurre a ETW Patching:

  1. El proceso localiza la función exportada ntdll!EtwEventWrite.
  2. Modifica los permisos de la página de memoria usando VirtualProtect a PAGE_EXECUTE_READWRITE.
  3. Sobrescribe el prólogo de la función con una instrucción de retorno anticipado:
    • En x64: xor eax, eax; ret (codificado como 31 C0 C3 por ensambladores GAS/NASM o 33 C0 C3 por MSVC/MASM) o simplemente ret (C3).
  4. Al retornar 0 (STATUS_SUCCESS), la aplicación cree que el evento se registró con éxito, pero ningún byte de telemetría llega al despachador de ETW.

Detección Defensiva: Un monitor de integridad lee la imagen limpia de ntdll.dll directamente desde el disco (\SystemRoot\System32\ntdll.dll) y compara los primeros 16 bytes de EtwEventWrite contra los bytes en memoria. Cualquier discordancia (0xC3, 0x31 0xC0 o 0x33 0xC0 en los primeros bytes) delata un parcheo activo de ETW.

B. Cegado en Modo Kernel (ETWti Blinding)

A nivel de kernel, los controladores de seguridad se alimentan del proveedor Microsoft-Windows-Threat-Intelligence (Lección 6.7). Para cegar este sensor:

  • Un atacante con primitiva de escritura en kernel (vector BYOVD) localiza el handle de registro apuntado por nt!EtwThreatIntProvRegHandle.
  • En la estructura _ETW_GUID_ENTRY, manipula el campo ProviderEnableInfo, estableciendo la máscara de habilitación a cero (EnableMask = 0).
  • Al quedar deshabilitado el proveedor a nivel de hipervisor/kernel, el sensor EDR deja de recibir eventos de inyección de hilos y acceso a memoria sin generar alertas visibles en user mode.

5. Repaso

¿Qué rol cumple el controller?

Define y controla una sesión ETW, habilita providers y establece cómo registrar eventos.

¿Qué diferencia provider y consumer?

El provider produce eventos; el consumer los lee e interpreta desde una sesión o archivo.

¿Una traza sin eventos prueba que no ocurrió actividad?

No. El provider puede no estar habilitado, no emitir ese evento, perder datos o haber sido parcheado (EtwEventWrite).

¿Qué es la sesión NT Kernel Logger?

Es la sesión del sistema reservada para telemetría de bajo nivel del kernel (procesos, hilos, DLLs, disco, red), controlada por SystemTraceControlGuid.

¿Cómo detectás en memoria un parcheo de ETW en user mode?

Comparando los primeros bytes de ntdll!EtwEventWrite en memoria contra los bytes del archivo original en disco; si empieza con 0xC3 o 0x31 0xC0, fue alterado.

Ampliación editorial basada en fuentes externas — Extracción estática del Provider GUID (EventRegister) y detección de ETW Patching

Al analizar un binario en IDA o Ghidra que interactúa con ETW, existen dos patrones opuestos: la telemetría legítima instrumentada por el desarrollador y el intento de malware de cegar la monitorización del sistema (Microsoft Learn: EventRegister y EtwEventWrite) (Hecho confirmado):

  1. Localización del Provider GUID en aplicaciones legítimas o instrumentadas:
    Al buscar referencias cruzadas a advapi32!EventRegister (o ntdll!EtwEventRegister), la firma en x64 recibe: 
    lea rcx, [rip + GUID_Provider] ; 1.er arg (RCX): Puntero a los 16 bytes del GUID en .rdata
xor edx, edx                   ; 2.º arg (RDX): EnableCallback (opcional)
xor r8d, r8d                   ; 3.er arg (R8) : CallbackContext
lea r9, [rip + g_RegHandle]    ; 4.º arg (R9) : Puntero global donde se guarda el REGHANDLE
call cs:EventRegister
    El valor guardado a través de R9 (REGHANDLE) es el manejador global que luego usarán todas las llamadas subsiguientes a EventWrite / EtwEventWrite para emitir eventos. Leer los 16 bytes apuntados por RCX permite cruzar de inmediato el GUID con logman query providers en la VM para conocer la identidad y finalidad del proveedor.
  2. Reconocimiento defensivo de ETW Patching en User-Mode:
    Ciertas muestras evasivas intentan silenciar la telemetría del propio proceso (como los eventos del runtime de .NET CLR o AMSI) resolviendo dinámicamente ntdll!EtwEventWrite (o NtTraceEvent), cambiando la protección de su página de memoria a PAGE_EXECUTE_READWRITE y sobrescribiendo su primer byte con ret (0xC3) o xor eax, eax ; ret (33 C0 C3). En el depurador, el analista lo detecta comparando los primeros bytes de ntdll!EtwEventWrite en memoria frente a la copia intacta de ntdll.dll en disco o monitoreando llamadas a VirtualProtect sobre rangos de memoria de ntdll.

5. ETW Threat Intelligence (Microsoft-Windows-Threat-Intelligence / ETWti)

Introducido para alimentar directamente a Microsoft Defender for Endpoint (MDE) y sensores EDR de terceros certificados por el programa MVI (Microsoft Virus Initiative), el proveedor Microsoft-Windows-Threat-Intelligence (ETWti) —identificado por el GUID {f4e1897c-bb5d-5668-f1d8-040f4d8dd344}— instrumenta directamente las syscalls de gestión de memoria virtual, mapeo de secciones y encolado de APCs dentro del propio ejecutivo ntoskrnl.exe.

5.1. Restricción de Consumo mediante PPL (PsProtectedSignerAntimalware-Light)

A diferencia de los proveedores ETW convencionales accesibles desde cualquier sesión de usuario, el registro de una sesión de traza contra el GUID de ETWti está restringido a nivel del kernel mediante una verificación de token protegido:

  • Únicamente procesos que ejecutan bajo el nivel Protected Process Light (PPL) con el firmante antimalware (PsProtectedSignerAntimalware-Light o superior) pueden suscribirse a este proveedor vía EnableTraceEx2.
  • Esta barrera impide que un binario no privilegiado o un atacante en Ring 3 intercepte los eventos generados por las rutinas de inyección de código de otros procesos.

5.2. Punteros en Kernel y Registro en WinDbg (nt!EtwThreatIntProvRegHandle)

Nota de entorno: Laboratorio verificado: no; requiere VM/toolchain. En una sesión de depuración con ntoskrnl.pdb, el puntero al registro del proveedor se almacena en el símbolo global nt!EtwThreatIntProvRegHandle (de tipo _ETW_REG_ENTRY*). Desde este objeto se inspecciona la estructura _ETW_GUID_ENTRY que controla qué palabras clave (keywords) de monitorización están habilitadas:

kd> x nt!EtwThreatIntProvRegHandle
ffffb609`120489a0 nt!EtwThreatIntProvRegHandle = 0xffffb609`102e3a10

kd> dt nt!_ETW_REG_ENTRY 0xffffb609`102e3a10 GuidEntry
   +0x020 GuidEntry : 0xffffb609`102f6840 _ETW_GUID_ENTRY

kd> dt nt!_ETW_GUID_ENTRY 0xffffb609`102f6840 Guid ProviderEnableInfo
   +0x018 Guid               : {f4e1897c-bb5d-5668-f1d8-040f4d8dd344}
   +0x060 ProviderEnableInfo : _TRACE_ENABLE_INFO
      +0x000 IsEnabled          : 0x1
      +0x004 Level              : 0xff ''
      +0x008 MatchAnyKeyword    : 0x80000000`ffffffff

Si un rootkit o driver en modo kernel sobrescribe el puntero nt!EtwThreatIntProvRegHandle con cero o modifica ProviderEnableInfo.IsEnabled = 0, ciega la telemetría de kernel que reciben los agentes EDR sin disparar inmediatamente un Bugcheck de PatchGuard (aunque kernels modernos protegen este handle mediante monitorización periódica de integridad).
