6-10 · Fuzzing de Drivers en Modo Kernel: Superficie IOCTL, Snapshot Fuzzing y Cobertura por Hardware

Nivel: Avanzado (Ring 0 / Hypervisor-Assisted) | Arquitectura: Windows 10 / 11 x64 | Laboratorio verificado: no; requiere VM/toolchain

1. Anatomía de la Superficie de Ataque en Drivers WDM y KMDF

La inmensa mayoría de vulnerabilidades alcanzables localmente en drivers de terceros (antivirus, utilidades de overclocking, anticheats y periféricos susceptibles a ataques Bring Your Own Vulnerable Driver — BYOVD) se exponen a través de paquetes de petición de E/S (IRP, estructura nt!_IRP) despachados hacia MajorFunction[IRP_MJ_DEVICE_CONTROL] (índice 0x0E) o su variante interna IRP_MJ_INTERNAL_DEVICE_CONTROL (0x0F).

Para que un proceso en Ring 3 (incluso con nivel de integridad Low o Medium) pueda enviar un IOCTL mediante la syscall NtDeviceIoControlFile, primero debe abrir un handle válido hacia el objeto de dispositivo (_DEVICE_OBJECT) invocando NtCreateFile sobre su enlace simbólico en el directorio de objetos \GLOBAL??\. Si el desarrollador omitió restringir el Security Descriptor (SDDL) mediante IoCreateDeviceSecure (WDK) o WdfDeviceInitAssignSDDLString (KMDF), cualquier usuario local podrá alcanzar la rutina de despacho.

1.1. Decodificación del Código de Control (CTL_CODE)

El parámetro IoControlCode (32 bits) almacenado en IrpSp->Parameters.DeviceIoControl.IoControlCode (donde IrpSp proviene de IoGetCurrentIrpStackLocation(Irp), estructura _IO_STACK_LOCATION) codifica cuatro campos críticos que determinan cómo el I/O Manager (`ntoskrnl.exe`) mapea y valida los buffers de usuario antes de ceder la ejecución al driver: 

// Definición estructural de un IOCTL (32 bits) en winioctl.h / wdm.h

// +------------------+------------+--------------+--------+

// |   DeviceType     |   Access   |   Function   | Method |

// |  Bits 31..16     | Bits 15..14|  Bits 13..2  |Bits 1.0|

// +------------------+------------+--------------+--------+



#define CTL_CODE(DeviceType, Function, Method, Access) ( \

    ((DeviceType) << 16) | ((Access) << 14) | ((Function) << 2) | (Method) \

)



#define METHOD_BUFFERED                 0

#define METHOD_IN_DIRECT                1

#define METHOD_OUT_DIRECT               2

#define METHOD_NEITHER                  3
Método (Bits 1..0) Puntero de Entrada en el IRP Puntero de Salida en el IRP Superficie de Fallo Característica
METHOD_BUFFERED (0) Irp->AssociatedIrp.SystemBuffer Irp->AssociatedIrp.SystemBuffer El I/O Manager aloja un único buffer en NonPagedPool del tamaño max(InputBufferLength, OutputBufferLength). Propenso a Pool Overflow si no se valida InputBufferLength y a Info Leak de memoria de kernel no inicializada si IoStatus.Information excede los bytes realmente escritos.
METHOD_IN_DIRECT (1) / METHOD_OUT_DIRECT (2) Irp->AssociatedIrp.SystemBuffer Irp->MdlAddress (mapeado con MmGetSystemAddressForMdlSafe) El buffer secundario se bloquea en páginas físicas mediante un _MDL (MmProbeAndLockPages). Sin embargo, las páginas físicas subyacentes siguen mapeadas en el espacio virtual de Ring 3: un hilo concurrente en modo usuario puede modificar el contenido en pleno procesamiento (condición TOCTOU / Double Fetch).
METHOD_NEITHER (3) IrpSp->Parameters.DeviceIoControl.Type3InputBuffer Irp->UserBuffer El I/O Manager entrega punteros virtuales crudos de Ring 3 sin validar. Si el driver no ejecuta ProbeForRead / ProbeForWrite dentro de un bloque SEH (__try / __except) y copia los datos a un buffer local antes de usarlos, permite primitivas directas de Arbitrary Kernel Read/Write (Write-What-Where) y Double Fetch.

2. Amplificación Determinista de Fallos: Driver Verifier y Special Pool

Un problema fundamental al hacer fuzzing contra el kernel es la corrupción silenciosa: un desbordamiento de 4 bytes sobre un bloque del Kernel Pool (ExAllocatePool2 / ExAllocatePoolWithTag) rara vez provoca un BugCheck en la instrucción exacta que escribe fuera de límites; en su lugar, corrompe los metadatos del chunk adyacente (_POOL_HEADER) o punteros de un objeto vecino, provocando un fallo asíncrono minutos después en un hilo del sistema completamente distinto.

Para transformar cualquier lectura o escritura fuera de límites de un solo byte en un BugCheck inmediato y atribuible a la instrucción culpable, es obligatorio activar Driver Verifier con la característica Special Pool sobre el driver auditado.

2.1. Mecánica a Nivel de PTE del Special Pool

Cuando el Special Pool intercepta una llamada a ExAllocatePoolWithTag / ExAllocatePool2 (para tamaños menores a una página, es decir, menos de 0xFE0 bytes), reserva un par de páginas virtuales contiguas en la región del Special Pool:

  • Página 1 (Asignación alineada al final): El bloque solicitado se coloca pegado al límite superior de la primera página de 4 KB (`0x1000`), y el resto inferior de la página se rellena con un patrón aleatorio repetido capaz de detectar underflows al liberar el bloque.
  • Página 2 (Guard Page Inmediata): La entrada de tabla de páginas (_MMPTE) de la página inmediatamente posterior tiene el bit Valid = 0 (no mapeada físicamente). Cualquier off-by-one hacia adelante cruza la frontera de página y dispara instantáneamente una excepción #PF (Page Fault) en la CPU, que el gestor de memoria traduce en DRIVER_PAGE_FAULT_BEYOND_END_OF_ALLOCATION (0xD6) o PAGE_FAULT_IN_NONPAGED_AREA (0x50) apuntando exactamente al RIP de la instrucción defectuosa.

3. Arquitecturas Modernas de Fuzzing en Ring 0

A diferencia de una aplicación de consola en modo usuario, un driver de kernel mantiene estado global en el sistema operativo, interactúa con el hardware y ante el primer fallo provoca un Blue Screen of Death (KeBugCheckEx) que requeriría decenas de segundos para reiniciar la máquina virtual. Las herramientas modernas resuelven esto mediante dos paradigmas complementarios:

3.1. Fuzzing Basado en Snapshots y Emulación Determinista: WTF (What The Fuzz)

Desarrollado por Axel "0vercl0k" Souchet, WTF desacopla la ejecución del caso de prueba del sistema operativo vivo:

  1. Se prepara un harness en la VM que abre el dispositivo del driver y se detiene justo antes de invocar NtDeviceIoControlFile (o en el punto de entrada de IRP_MJ_DEVICE_CONTROL).
  2. Con WinDbg conectado por red (KDNET), se toma un volcado completo de memoria activa y estado de registros de la CPU mediante la extensión !dmp (generando un estado base determinista).
  3. WTF carga dicho volcado sobre un backend de ejecución ultrarrápido (Bochs para emulación pura multiplataforma o KVM / Hyper-V WHPX para ejecución nativa asistida por virtualización).
  4. En cada iteración (alcanzando miles de ejecuciones por segundo por núcleo), WTF inyecta el buffer mutado en la memoria del proceso/IRP, ejecuta hasta alcanzar un breakpoint de retorno (por ejemplo, IofCompleteRequest) o un hook en nt!KeBugCheck2 / nt!KiPageFault, registra las nuevas aristas de código descubiertas y restaura únicamente las páginas de memoria física ensuciadas (dirty pages) en microsegundos.

3.2. Fuzzing Guiado por Cobertura de Hardware con Intel PT: kAFL y Nyx

Cuando el driver realiza operaciones complejas de sincronización multi-hilo, timers de kernel (DPCs) o interacción con subsistemas difíciles de contener en un micro-snapshot, se emplea kAFL / Nyx sobre KVM-PT:

  • Trazado sin instrumentación binaria: El hipervisor configura los registros MSR de Intel Processor Trace (Intel PT) (`IA32_RTIT_CTL`) filtrando por el rango de direcciones virtuales (`CR3` o rangos de IP en Ring 0 correspondientes a `target_driver.sys`).
  • Decodificación en el Host: La CPU graba paquetes comprimidos de saltos condicionales (paquetes TNT — Taken/Not-Taken) y saltos indirectos (TIP — Target IP) directamente en un buffer físico del hipervisor con menos de un 5% de sobrecarga.
  • Snapshots rápidos en Hypervisor (Nyx): Un agente ligero en Ring 3 dentro de la VM se comunica mediante hiperllamadas (vmcall) con QEMU-PT/Nyx para solicitar un fast-reload de las páginas sucias del EPT tras cada serie de llamadas IOCTL o en cuanto el hook de KeBugCheckEx detecta un fallo.

4. Laboratorio Práctico: Desarrollo de Harness para WTF y Triaje de Pool Overflow

Declaración de Entorno: Laboratorio verificado: no; requiere VM/toolchain. Para reproducir este laboratorio se requiere una máquina Host con soporte de virtualización anidada o CPU compatible con Bochs/WHPX, SDK de Windows (WinDbg Preview), el repositorio oficial de WTF (0vercl0k) y una VM Guest Windows 11 x64 con Driver Verifier activo sobre el driver de pruebas (p. ej., HEVD.sys — HackSys Extreme Vulnerable Driver).

Paso 1: Captura del Estado Base (Target Harness en Guest VM)

El siguiente programa se ejecuta en la VM Guest. Reserva páginas de memoria bloqueadas en RAM física (VirtualLock) para garantizar que tanto el código del harness como el buffer de entrada estén presentes en las tablas de páginas al momento de volcar el estado con WinDbg: 

// harness_ioctl_snapshot.c — Compilar en x64 Release sin optimizaciones agresivas

#include <windows.h>

#include <stdio.h>



#define DEVICE_SYMLINK L"\\\\.\\HackSysExtremeVulnerableDriver"

#define HEVD_IOCTL_BUFFER_OVERFLOW_NON_PAGED_POOL CTL_CODE(0x22, 0x803, METHOD_NEITHER, FILE_ANY_ACCESS)

#define MAX_FUZZ_SIZE 0x1000



#pragma optimize("", off)

int main(void) {

    HANDLE hDevice = CreateFileW(

        DEVICE_SYMLINK,

        GENERIC_READ | GENERIC_WRITE,

        FILE_SHARE_READ | FILE_SHARE_WRITE,

        NULL,

        OPEN_EXISTING,

        FILE_ATTRIBUTE_NORMAL,

        NULL

    );



    if (hDevice == INVALID_HANDLE_VALUE) {

        printf("[-] Error abriendo el dispositivo: %lu\n", GetLastError());

        return 1;

    }



    PVOID FuzzBuffer = VirtualAlloc(NULL, MAX_FUZZ_SIZE, MEM_COMMIT | MEM_RESERVE, PAGE_READWRITE);

    VirtualLock(FuzzBuffer, MAX_FUZZ_SIZE);

    RtlFillMemory(FuzzBuffer, MAX_FUZZ_SIZE, 0x41);



    DWORD BytesReturned = 0;



    // Dispara interrupción en el depurador de kernel justo antes del syscall

    __debugbreak();



    DeviceIoControl(

        hDevice,

        HEVD_IOCTL_BUFFER_OVERFLOW_NON_PAGED_POOL,

        FuzzBuffer,

        MAX_FUZZ_SIZE,

        NULL,

        0,

        &BytesReturned,

        NULL

    );



    return 0;

}

#pragma optimize("", on)

Paso 2: Módulo de Inserción de Caso de Prueba y Hooks en WTF

En el motor de WTF, el script del objetivo intercepta el estado justo en el int 3 (`__debugbreak()`), reemplaza el contenido de FuzzBuffer y el tamaño nInBufferSize pasado a DeviceIoControl, y coloca hooks de detención tanto al regresar a modo usuario como en las rutinas de pánico del kernel: 

// target_hevd_wtf.cc — Fragmento de configuración de hooks en WTF

bool Init(const Options_t &Opts, const CpuState_t &State) {

    // 1. Detener la iteración y marcar CRASH si el kernel invoca KeBugCheck2 o ExRaiseAccessViolation

    if (!g_Backend->SetBreakpoint("nt!KeBugCheck2", [](Backend_t *Backend) {

        Backend->Stop(Crash_t( Backend->GetFormat("BugCheck_%llx", Backend->Rcx()) ));

    })) {

        return false;

    }



    // 2. Avanzar desde __debugbreak() hasta la llamada a DeviceIoControl e inyectar el testcase

    // En la convención x64 de Windows, al entrar en kernel32!DeviceIoControl:

    //   RCX = hDevice

    //   RDX = dwIoControlCode

    //   R8  = lpInBuffer

    //   R9  = nInBufferSize

    if (!g_Backend->SetBreakpoint("kernelbase!DeviceIoControl", [](Backend_t *Backend) {

        const uint8_t *TestcaseBuffer = nullptr;

        size_t TestcaseSize = 0;

        Backend->GetTestcase(TestcaseBuffer, TestcaseSize);



        if (TestcaseSize < sizeof(uint32_t) || TestcaseSize > 0x1000) {

            Backend->Stop(Ok_t());

            return;

        }



        Gva_t InBufferGva = Gva_t(Backend->R8());

        uint32_t PayloadLen = static_cast<uint32_t>(TestcaseSize);



        // Escribir el payload mutado directamente en la memoria virtual del proceso

        if (!Backend->VirtWriteDirty(InBufferGva, TestcaseBuffer, PayloadLen)) {

            Backend->Stop(Ok_t());

            return;

        }

        Backend->R9(PayloadLen);

    })) {

        return false;

    }



    return true;

}
