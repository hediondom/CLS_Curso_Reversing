2D-17 · Virtualization-Based Security (VBS) Profundo: VTL 1, Secure Kernel (`securekernel.exe`), HVCI y Trustlets (IUM)

Nivel: Avanzado (Ring -1 / VTL 1 / VTL 0) | Arquitectura: Windows 10 / 11 x64 (Hyper-V SLAT / EPT / NPT) | Laboratorio verificado: no; requiere VM/toolchain

1. Ortogonalidad de Privilegios: Anillos de CPU vs. Virtual Trust Levels (VTL)

Históricamente, el modelo de seguridad de Windows descansaba sobre el supuesto de que el código ejecutándose en Ring 0 (ntoskrnl.exe y los drivers cargados) constituía la frontera máxima de confianza (Trusted Computing Base — TCB). En cuanto un atacante explotaba un driver vulnerable (BYOVD) o una vulnerabilidad en win32kfull.sys para obtener una primitiva de lectura/escritura arbitraria en Ring 0, podía desactivar g_CiOptions en ci.dll, recorrer la lista ActiveProcessLinks para elevar tokens o extraer secretos criptográficos de lsass.exe.

Virtualization-Based Security (VBS) rompe este paradigma utilizando el hipervisor de Microsoft (Hyper-V, ejecutándose en VMX Root Mode / Ring -1 a través de hvix64.exe en Intel o hvax64.exe en AMD) para particionar la máquina virtual raíz (Root Partition) en niveles de confianza virtuales ortogonales denominados Virtual Trust Levels (VTLs): 

+-----------------------------------------------------------------------------------+

|                     ESPACIO DE CONFIANZA DE WINDOWS (ROOT PARTITION)              |

+-----------------------------------------+-----------------------------------------+

|        VTL 0 (Normal World)             |          VTL 1 (Secure World)           |

+-----------------------------------------+-----------------------------------------+

| Ring 3: Procesos de Usuario Estándar    | Ring 3: Isolated User Mode (IUM)        |

|   - explorer.exe, navegador, apps       |   - Trustlets: lsaiso.exe (CredGuard)   |

|   - lsass.exe (Normal World portion)    |   - Trustlets: skci / Biometrics / TPM  |

+-----------------------------------------+-----------------------------------------+

| Ring 0: Ejecutivo NT Estándar           | Ring 0: Secure Kernel                   |

|   - ntoskrnl.exe, win32k.sys, hal.dll   |   - securekernel.exe                    |

|   - ci.dll, drivers WDM/KMDF terceros   |   - skci.dll (Secure Code Integrity)    |

+-----------------------------------------+-----------------------------------------+

|       Tabla SLAT / EPT #0 (VTL 0)       |       Tabla SLAT / EPT #1 (VTL 1)       |

+-----------------------------------------+-----------------------------------------+

|              HIPERVISOR HYPER-V (Ring -1 / VMX Root: hvix64.exe)                  |

+-----------------------------------------------------------------------------------+

El aislamiento entre VTL 0 y VTL 1 no depende de las tablas de páginas del sistema operativo (`CR3` / `PML4`), ya que `ntoskrnl.exe` en VTL 0 tiene control total sobre su propio `CR3`. En cambio, el hipervisor mantiene **dos conjuntos independientes de tablas SLAT** (Second Level Address Translation: **EPT** en Intel, **NPT** en AMD). Las páginas físicas asignadas a VTL 1 (`securekernel.exe`, `skci.dll` y procesos IUM) tienen sus entradas marcadas como **No Presentes (`---`)** en la tabla EPT de VTL 0. Si un rootkit en Ring 0 (VTL 0) intenta mapear la dirección física (SPA/GPA) de VTL 1 mediante `MmMapIoSpace` o construyendo una PTE manual, la CPU genera inmediatamente una **EPT Violation (`VMEXIT`)** interceptada por Hyper-V, bloqueando el acceso.

2. El Secure Kernel (`securekernel.exe`) y el Puente de Transición VTL

Cuando VBS está activo, el cargador de arranque (winload.efi) inicializa tanto VTL 1 como VTL 0 antes de transferir el control a ntoskrnl.exe. En VTL 1 reside un micro-ejecutivo especializado: securekernel.exe. A diferencia de ntoskrnl.exe, el Secure Kernel no implementa un subsistema gráfico, ni pila de red, ni sistema de archivos, ni permite la carga de drivers de terceros; su única función es administrar la memoria de VTL 1, orquestar la ejecución de los procesos IUM (Trustlets) y exponer servicios criptográficos y de integridad a VTL 0.

2.1. Anatomía de una Transición VTL 0 → VTL 1 (`VtlCall`)

Un procesador lógico (VP — Virtual Processor) ejecuta en VTL 0 o en VTL 1 en un instante dado. Cuando ntoskrnl.exe necesita solicitar un servicio a securekernel.exe (por ejemplo, validar una página de código con HVCI o proteger una estructura crítica mediante Kernel Data Protection — KDP), ejecuta la siguiente secuencia:

  1. Empaquetado en VTL 0: ntoskrnl.exe invoca nt!VslpEnterIumSecureMode rellenando un bloque de transferencia (Secure Call Parameter Block) con el código de operación (SecureServiceId) y los argumentos.
  2. Hiperllamada (`HvCallVtlCall`): Se invoca la rutina de la página de hiperllamadas (nt!HvcallCodeVa) que ejecuta la instrucción vmcall (Intel) o vmmcall (AMD) con el código de hiperllamada HvCallVtlCall (0x0011).
  3. Conmutación en el Hipervisor (`hvix64.exe`): Hyper-V intercepta el VMEXIT, guarda el contexto de registros de VTL 0 (incluyendo `RIP`, `RSP`, `CR3` y MSRs en la estructura del procesador virtual), conmuta el puntero EPT (`EPTP`) del VMCS hacia la tabla EPT de VTL 1 y reanuda la ejecución (`VMRESUME`) en el punto de entrada registrado de VTL 1 (`securekernel!SkKiVtlCall`).
  4. Retorno a VTL 0 (`HvCallVtlReturn`): Una vez completada la operación en `securekernel.exe`, VTL 1 invoca `HvCallVtlReturn (0x0012)`, restaurando el contexto y la tabla EPT de VTL 0.

3. HVCI (Hypervisor-Protected Code Integrity) y la Política W^X en EPT

Sin VBS, el módulo de integridad de código (ci.dll) corre en VTL 0 junto con el resto del kernel. Un atacante con escritura arbitraria en Ring 0 simplemente sobrescribe la variable global ci!g_CiOptions (poniéndola a 0x0) para deshabilitar DSE (Driver Signature Enforcement) y cargar un driver sin firma.

Con HVCI (también denominado Memory Integrity en Windows Security), la lógica crítica de verificación criptográfica se traslada a skci.dll dentro de VTL 1, y el hipervisor impone una política estricta W^X (Write XOR Execute) a nivel de SLAT/EPT para toda la memoria accesible por VTL 0:

Estado de la Página Física Permisos en Tabla de Páginas de VTL 0 (`PTE`) Permisos en Tabla SLAT / EPT de VTL 0 Comportamiento ante Intento de Explotación en Ring 0
Datos del Kernel (NonPagedPoolNx, Stack, .data) RW- (`NX = 1`, `Write = 1`) RW- (`EPT_READ | EPT_WRITE`) Incluso si un atacante en Ring 0 modifica la PTE en VTL 0 para poner `NX = 0` e intenta saltar a su shellcode en el Pool, el procesador sufre un `EPT Violation` porque la tabla EPT del hipervisor carece del permiso `EPT_EXECUTE`.
Código de Kernel Verificado (`.text` de `ntoskrnl.exe` y drivers) R-X (`NX = 0`, `Write = 0`) R-X (`EPT_READ | EPT_EXECUTE`) Si un rootkit desactiva el bit `WP` (`CR0.WP = 0`) o remapea la página física mediante una nueva MDL/PTE con permiso de escritura para instalar un *inline hook* en `ntoskrnl.exe`, el intento de escritura falla en el hardware por ausencia de `EPT_WRITE`.

3.1. Flujo de Validación de una Página Ejecutable (`VslVerifyPage`)

Cuando ntoskrnl.exe carga un nuevo driver en VTL 0, ci.dll no puede otorgar permisos de ejecución por sí mismo. En su lugar, realiza una llamada VTL hacia skci.dll (`SkciValidateImagePages`). skci.dll mapea las páginas físicas de la imagen en VTL 1, revoca temporalmente el permiso de escritura de VTL 0 sobre dichas páginas en el EPT (para impedir condiciones de carrera TOCTOU desde VTL 0), calcula el hash SHA-256 de la página comparándolo con el catálogo firmado o la tabla de hashes del certificado PE, y solo si es válido solicita a Hyper-V (`HvModifySparseGpaPageHostVisibility` / `HvCallModifyVtlProtectionMask`) que active el bit `EPT_EXECUTE` manteniendo `EPT_WRITE = 0`.

4. Isolated User Mode (IUM) y Credential Guard (`lsaiso.exe`)

En Ring 3 de VTL 1 se ejecutan los Trustlets (procesos IUM). Un Trustlet se compone de dos mitades coordinadas por el sistema:

  • Un contenedor objeto _EPROCESS en VTL 0 marcado con el bit MinimalProcess = 1 (sin páginas de usuario legibles en VTL 0, sirviendo únicamente para que el planificador de hilos de `ntoskrnl.exe` pueda asignar tiempo de CPU a sus hilos `_ETHREAD`).
  • Una estructura de proceso seguro (_SKPROCESS) dentro de securekernel.exe en VTL 1, cuyas páginas de código y pila residen exclusivamente en memoria física protegida por la tabla EPT de VTL 1.

El caso de uso emblemático es Credential Guard (`lsaiso.exe`). Cuando un usuario inicia sesión, lsass.exe (en VTL 0) nunca almacena en texto claro el hash NTLM ni las claves de largo plazo de Kerberos en su propio heap; en su lugar, los envía por un canal RPC/ALPC inter-VTL hacia el Trustlet lsaiso.exe (en VTL 1). Si un atacante con privilegios `SYSTEM` o acceso de driver en VTL 0 vuelca la memoria de `lsass.exe` con Mimikatz o `MiniDumpWriteDump`, únicamente obtiene blobs cifrados cuya clave maestra reside exclusivamente dentro de `securekernel.exe` / `lsaiso.exe` en VTL 1.
